Stop Relying on Paid Alerts: Deploy Gotify for Instant Phone Notifications

TS
By Tech Simpld
•
September 2026
•
9 Min Read

I used to rely on Pushover and a messy chain of SMTP relays to know when my Proxmox cluster dropped a node or Nextcloud stopped syncing. The problem? Subscriptions add up, and emails get buried under spam. When my primary backup disk failed last year, I didn't find out until I went looking for a file two days later.

That is when I ripped out the paid services and deployed Gotify. Gotify is a completely free, open-source, self-hosted notification server written in Go. It runs in the background using almost zero resources and pushes real-time alerts straight to your phone via WebSockets. You control the server, you control the data, and there are absolutely no usage limits or API fees.

In this guide, I will show you exactly how I deploy Gotify via Docker Compose, set up application tokens, hook it natively into Proxmox VE, and write custom bash scripts that alert you before a minor hiccup becomes a full-blown outage.

Prerequisites / Environment

Before we dive into the deployment, ensure your home lab environment has the following pieces in place:

  • A Home Server or VM: Running a modern Linux distribution (Debian, Ubuntu) with Docker and Docker Compose installed.
  • Reverse Proxy (Optional but highly recommended): Caddy, Nginx Proxy Manager, or a Cloudflare Zero Trust Tunnel. You will need this to securely expose Gotify to the outside world if you want push notifications while away from your home Wi-Fi network without connecting to a VPN.
  • Android Device: The official Gotify client is Android-only. If you use iOS, you will need a third-party client workaround like Forwarder, though this guide focuses on the native Android experience.

Step-by-Step Implementation

1. Architecting the Docker Compose Stack

I prefer to keep all my Docker container data organized in a single structure. Deploying Gotify via Docker Compose is the cleanest, most reproducible method. First, create the directory structure on your server: 

mkdir -p /opt/docker/gotify && cd /opt/docker/gotify

Create a file named docker-compose.yml and paste in the following configuration: 

services:
  gotify:
    image: gotify/server:latest
    container_name: gotify-server
    restart: unless-stopped
    ports:
      - "8080:80"
    environment:
      - GOTIFY_DEFAULTUSER_PASS=ChangeThisPassword123
      - TZ=America/New_York
    volumes:
      - ./data:/app/data

Why configure it this way?

  • image: I specify gotify/server:latest to ensure I am on the most stable branch.
  • environment: The default admin password needs to be set immediately. Do not leave this as "admin". I also hardcode the Timezone (TZ) so message timestamps accurately reflect my local time. There is nothing worse than auditing server logs and trying to calculate UTC offsets in your head at 2 AM.
  • volumes: Gotify uses a lightweight SQLite database stored in /app/data. By binding this to a local ./data directory, I guarantee that my configuration, user accounts, and message history survive container updates and migrations.

Run the container in detached mode: 

docker compose up -d

2. Initial Setup and App Tokens

Navigate to http://YOUR-SERVER-IP:8080 in your browser. Log in using admin and the password you defined in the Compose file.

Gotify revolves around "Applications." Think of an Application as an individual sender. You do not want Proxmox and your Uptime Kuma instance sharing the same identity. By isolating them, you can revoke one token if it is compromised without breaking your entire alerting pipeline. It also allows you to give custom icons to different services.

  1. Navigate to the Apps tab.
  2. Click Create Application.
  3. Name it "Proxmox Cluster" and hit Create.
  4. Gotify will generate a Token starting with A. Copy this; we need it for the next steps.

3. Native Integration with Proxmox VE

One of the massive wins for Gotify is its native integration in Proxmox VE 8.1 and higher. I no longer need to write custom wrapper scripts just to find out if a VM snapshot failed.

Here is how I configure it on my cluster:

  1. Go to Datacenter → Notifications → Notification Targets.
  2. Click Add and choose Gotify.
  3. Name the target gotify-alerts.
  4. Enter your Server URL (e.g., http://192.168.1.50:8080).
  5. Paste your Application Token.
  6. Click Test. You should instantly see a test message hit your Gotify dashboard.

Next, I set up a Notification Matcher in Proxmox to route critical events (like backup failures or HA fencing actions) directly to this target.

4. Custom Script Alerts

The real beauty of Gotify is its raw REST API. Anything that can send an HTTP POST request can trigger an alert. Here is the exact bash function I drop into my maintenance scripts: 

send_gotify_alert() {
  local TITLE="$1"
  local MESSAGE="$2"
  local PRIORITY="$3"
  local URL="http://192.168.1.50:8080/message"
  local TOKEN="Axxxxxxxxxxxxxx"

  curl -s -X POST "$URL" \
    -H "X-Gotify-Key: $TOKEN" \
    -F "title=$TITLE" \
    -F "message=$MESSAGE" \
    -F "priority=$PRIORITY" > /dev/null
}

# Implementation example in a backup script
echo "Starting rsync task..."
if rsync -avz /data/ /backup/; then
  send_gotify_alert "Backup Success" "Nightly rsync completed cleanly." 2
else
  send_gotify_alert "BACKUP FAILURE" "Critical: rsync encountered an error." 9
fi

Notice the priority flag. Gotify uses this to dictate how your phone handles the alert. I use 2 for successful jobs—they silently drop into my notification drawer. I use 9 for failures, which override Do Not Disturb on my phone and trigger a loud, persistent alarm.

Troubleshooting & Edge Cases

If you deploy this in a real home lab, you will eventually hit a snag. Here are the common pitfalls I have run into and exactly how to fix them:

WebSocket Disconnections Behind a Reverse Proxy:

If you expose Gotify via Nginx Proxy Manager or Caddy, you might notice notifications stop pushing to your phone after a few hours, requiring you to manually open the app to sync them. This happens because the reverse proxy isn't configured to pass WebSocket upgrade headers, causing the persistent connection to time out.

The Fix: Ensure Upgrade $http_upgrade and Connection "upgrade" are set in your proxy host configuration. In Nginx Proxy Manager, simply toggle the "WebSockets Support" switch to ON in your proxy host details.

Android Battery Optimization Killing the App:

Modern Android versions aggressively kill background apps to save battery life. Since the Gotify client maintains a persistent background WebSocket connection, Android will eventually sever it to save power.

The Fix: Go into your Android settings → Apps → Gotify → App Battery Usage → Set to "Unrestricted". This guarantees the OS leaves the connection alone.

Locked Out After a Container Update:

Occasionally, migrating to a new server or a major version bump in the Gotify Docker image can result in permissions issues reading the SQLite database, effectively locking you out.

The Fix: Always ensure the ./data directory is owned by the correct user running the Docker daemon. Running sudo chown -R 1000:1000 ./data usually resolves permission mismatches.

Conclusion / Next Steps

Gotify is a set-and-forget piece of infrastructure that pays massive dividends the first time it alerts you to a failed drive or a downed container. It gives me absolute control over my data and removes my dependency on rate-limited cloud APIs.

Now that Gotify is running and tested locally, your next step should be exposing it securely. I highly recommend wrapping it in a Cloudflare Zero Trust Tunnel so you can receive alerts securely anywhere in the world without opening a single port on your router's firewall.
